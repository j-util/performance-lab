## Contract and compatibility

The implementation uses synchronous `System.arraycopy`, independent column
arrays/counts, and no retained source-array field. Distinct-column writers
share only the atomic mode selection; callers serialize each column and join
before sealing. There is no executor policy in CPS. Positive row/batch and
column modes remain exclusive. Size stays zero until equal counts are validated;
a mismatch preserves data and allows corrective filling. No missing values
are synthesized. Existing row and typed-batch paths remain supported.

The existing tests covered whole/ranged copying, shallow reference identity,
null/all-null columns, invalid/null input, overflow, mode exclusivity, mismatch
recovery, untouched/one-column stores, post-seal calls, independent concurrent
growth and generated-name collisions. Two new tests cover nonzero empty boundary
ranges and invalid primitive/reference calls after partial filling, including
source reuse, count preservation, read gating and repeated seal.

No runtime correctness defect or API redesign was needed. Generated Javadocs
now correctly qualify row-mode rejection as applying to non-empty appends.

The normal generated-compatibility test retains its self-contained 1.2 fixture.
The optional published-baseline path downloads neither artifacts nor credentials;
it accepts two explicit JAR paths and invokes an external javac. Isolation is
necessary: the first in-process attempt selected the current processor through
parent-first loading, and the incompatible-return fixture caught that mistake.
The corrected test compiled with the actual Central 1.2.0 processor, ran the
same precompiled consumer on 1.2.0 and the candidate, recompiled the consumer
and a decorator unchanged, and verified the default UnsupportedOperationException
on a precompiled external implementation.

japicmp 0.25.4 found no incompatible public source/binary API changes in either
artifact or a clean Trade schema generated by both processors. The core public
API is unchanged. The appender/default are additions to generated stores.
The documented Java source boundary remains: an external implementation with
an existing incompatible zero-argument columnAppender() return type, or a
conflicting inherited default, may need changes. Universal source compatibility
is not claimed.

## Benchmark provenance and boundaries

The existing `HardwoodMaterializationBenchmark` contains the previous batch,
executor-backed and ArrayList comparison (history includes `c6e212a`, Concurrent
batch import). It includes Parquet access/decoding and remains separate.
The retained-array destination-only suite was introduced at `762a105`, with
barrier/pipelined methods at `4afe643` and virtual-thread variants at `f9b2767`.
Historical numbers are context only; all numbers below are new measurements.
No performance-lab restructuring, CodSpeed, Bencher or speculative optimization
was added.

All compared paths use the same deterministic schema: two long, three double
and three String columns. Source arrays are built once per trial outside timing.
Every invocation creates a fresh destination at exact row capacity. Columnar
paths copy the same half-open ranges and seal. ArrayList constructs one immutable
row per record. Fixed-pool mode uses eight platform workers, an ordered future
chain per column and one final join before seal. The executor is trial-owned;
submission, scheduling and joining are measured. Results return to JMH's
blackhole; validation scans are outside timing. Virtual-thread variants remain
available but are excluded from this release matrix.

Environment: macOS 26.6.2 build 25G83, Apple M4, 10 physical/logical CPUs,
24 GiB RAM; native Temurin 25.0.2+10-LTS; JMH 1.37. One benchmark thread,
G1, -Xms2g -Xmx4g. Maven Wrapper resolves 3.9.6 for CPS and 3.9.16
for performance-lab. Source arrays, allocation, GC and memory bandwidth all affect
this repeated-construction result; allocated B/op is not retained heap.

The preregistered matrix uses both 8,192-row chunks (destination default) and
1,000,000-row chunks (existing loader default), at 100,000 and 10,000,000 rows.
Five one-second warmups, eight one-second measurements, three forks; independent
10M repeat uses the same settings. Error is JMH's 99.9% confidence half-width.
Per-fork means are reported to expose variation. Relative differences are
(time / typed-batch time - 1); negative is faster. MiB/op is B/op / 1,048,576.

## Readiness verdict: BLOCKED

Correctness, API compatibility, clean consumer use, local packaging and exact-SHA
Java 8/26 CI passed. The required stable large-workload performance benefit did
not pass. Small-workload wins/losses do not determine this verdict.

The large columnar measurements have extremely wide confidence intervals and
large differences among forks. The independent repeat does not establish a
repeatable advantage of either appender over the existing typed-batch baseline.
The displayed relative percentages are arithmetic comparisons of unstable
means, not claims of speedup or regression. All timings and profiler samples
are retained; no outlier trimming or favorable-fork selection was used.

The measured immediate cause is GC-associated latency spikes in the repeated
520 MB destination allocation workload. For example, the primary 10M/8192
fixed-pool run measured 2,601.167 ms/op in one iteration with 2,544 ms reported
GC time, and a synchronous iteration measured 2,829.875 ms/op with 2,749 ms GC
time. Later iterations were much faster. The nominal five one-second warmups
did not stabilize this large-allocation regime sufficiently for a release
performance claim. Allocation remains consistent at about 496–497 MiB/op for
columnar destinations versus 648.5 MiB/op for ArrayList; this is not a latency
claim and the typed-batch baseline already has the same allocation advantage.

Smallest next investigation: keep source data, code, capacities, chunk sizes,
heap flags and collector unchanged; repeat the 10M typed-batch/fixed-pool pair
with longer warmup and per-fork GC logs. Verify an iteration plateau before
measurement, and identify which collections account for the multi-second
spikes. Only then repeat the controlled comparison. Do not redesign or optimize
the library based on these unstable aggregates.

No artifacts were published, no tag or GitHub release was created, no version
was changed to 1.3.0, and issue #7 remains open.
